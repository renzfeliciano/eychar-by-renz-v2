# People

**Purpose:** the Person record: a real human's identity and personal details (name, contact, gender, birth date, statutory IDs), kept apart from the User account and the Employee record, plus the read-only "other modules' records" loaders that feed the profile tabs.
**Governing docs:** ADR-003 (User vs Person vs Employee), ADR-019 (roster fields kept on the Person/Employment split), ADR-047 (everything about an employee on their profile), ARCHITECTURE.md § Identity model (ADR-003) and § Workforce (Phase 3), ENGINEERING.md § 13 (People model), § 35 (audit), § 37 (domain services).
**Services:**
- `src/domains/people/person-service.ts`: `PersonService.create(input, actor)`, `PersonService.update(personId, organizationId, patch, actor)`. Empty string in a patch means `$unset`, not `""` (lines 90-99). Audit `person.created` / `person.updated` with before/after (lines 53-60, 108-116).
- `src/domains/people/employee-records.ts`: `EmployeeRecords.payslips`, `travelOrders`, `offboarding`, `reviewCycleNames`. Read-only; each loads only when its profile tab opens (comment at lines 126-130). `offboarding` joins `ClearanceCaseModel`, `FinalSettlementModel` and `SeparationTypeService.listCurrent`; `payslips` joins `PayrollRecordModel` and `PayrollRunModel` and drops cancelled runs.

**Models:**
- `src/server/db/models/person.ts` (`PersonModel`): `organizationId`, names, `email`, `phone`, `gender` enum Male/Female, `birthDate`, `address`, `remarks` (max `REMARKS_MAX_LENGTH`), `educationLevelCode` (code of an `education-levels` catalog item, checked by `PersonService` against the active catalog before any write), `sssNumber`, `philHealthNumber`, `pagIbigNumber`, `tinNumber`, `pwdIdNumber` + `pwdIdValidUntil`, `soloParentIdNumber` + `soloParentIdValidUntil` (numbers max 50 characters, dates are `Date`; added 2026-11-16), `metadata`. No hidden plugin. **`rdoCode` and `zipCode` were removed 2026-11-16** (owner: not relevant); `scripts/remove-employee-rdo-zip.ts` (logic in `src/domains/people/remove-employee-rdo-zip.ts`) unsets the old values (dry run by default, `--apply`; it reads the raw collection because the schema no longer has those paths).
- Educational background: `src/domains/people/education-record-service.ts` (`EducationRecordService.listForEmployee/create/update/remove`, `toEducationRecordView`) over `src/server/db/models/education-record.ts` (`EducationRecord`: `personId`, `levelCode`, `school`, `course?`, `yearGraduated?`; several per level allowed). Routes `POST /api/employees/[id]/education`, `PATCH`/`DELETE .../[recordId]` (`employees.update`). Card: `src/app/(app)/people/[id]/education-background-card.tsx`. Rules: entry must belong to the employee in the URL; level checked against the active catalog only when it changes; year 1900..next year; blank course/year stored as absent; employee deletion moves the entries to the recycle bin with the employee and restores them (deletion-registry `planEmployee`); the level is checked on update only when it changes, since the edit form re-sends it; removal is a plain delete, audited (`education-record.created/updated/removed`).
- Additional government IDs (driver's license, passport, UMID and so on): `GovernmentIdRecordService` (`src/domains/people/government-id-record-service.ts`: `listForEmployee`, `create`, `update`, `remove`, `toGovernmentIdRecordView`) over `src/server/db/models/government-id-record.ts` (`GovernmentIdRecord`: `personId`, `typeCode?` or `otherTypeName?` (exactly one), `idNumber`, `validUntil?`). The type is a code from the `government-id-types` catalog, or a typed name when HR picks "Other". Routes `POST /api/employees/[id]/government-ids`, `PATCH`/`DELETE .../[recordId]`. Card `government-ids-card.tsx` (titled "Additional government IDs", because the existing "Government IDs" card holds SSS, PhilHealth, Pag-IBIG and TIN), dialog `government-id-dialog.tsx`.
- PRC licenses: `ProfessionalLicenseRecordService` (`professional-license-record-service.ts`, same four methods) over `professional-license-record.ts` (`ProfessionalLicenseRecord`: `personId`, `professionCode` (a `prc-professions` catalog code), `licenseNumber`, `validUntil?`). Routes `POST /api/employees/[id]/prc-licenses`, `PATCH`/`DELETE .../[recordId]`. Card `prc-licenses-card.tsx`, dialog `prc-license-dialog.tsx`.
- Shared by both: `valid-until.ts` (`cleanValidUntil`: a real `YYYY-MM-DD` day, blank/`null` means none, stored as UTC midnight), `expiry-status.ts` (`expiryStatus`: `expired` before today, `expiring` from today through 30 days, `valid`, `null` without a date) and `expiry-chip.tsx` (the "Expired" / "Expiring soon" chip).
- `src/domains/people/id-expiry-service.ts`: `IdExpiryService.listExpiring(organizationId, until, { employeeIds? })`, the dashboard's source for PWD, Solo Parent, government ID and PRC license dates (up to 200 per source, newest dates first). Without `employeeIds` it returns one item per employee record of the person; with it (the dashboard passes current staff) it reads only those employees' items and keeps the newest record per person. An empty list returns nothing.
- Read through: `EmployeeModel`, `EmployeeAssignmentModel`, `TravelOrderModel`, `ClearanceCaseModel`, `FinalSettlementModel`, `PayrollRecordModel`, `PayrollRunModel`, `ReviewCycleModel` (`src/server/db/models/index.ts`).

**Rules a change must respect:**
- A Person is never edited through the Employee record. Identity fields go through `PersonService.update` (`person-service.ts`, `update`), which scopes by `organizationId` and throws `NotFoundError` otherwise.
- Clearing a field must send `""`, which `PersonService.update` converts to `$unset`. Writing `""` with `$set` would leave the old value (comment at `person-service.ts` lines 90-92). Keep the `clearable` wrapper in `updateEmployeeProfileSchema` in step with this.
- Every Person write is audited, with before and after snapshots (`person-service.ts`, `AuditService.record`).
- Statutory IDs (`sssNumber`, `philHealthNumber`, `pagIbigNumber`, `tinNumber`) are format-validated at the service boundary (`src/shared/validation/shared.ts`, as noted in `src/server/db/models/person.ts` lines 17-18), not in the schema. Any new write path must go through the same validators.
- `EmployeeRecords` loaders must filter on `organizationId` (every query in `employee-records.ts` does). Keep that rule for any new loader.
- The PWD and Solo Parent validity dates in `updateEmployeeProfileSchema` use `validUntilDateSchema` (`src/shared/validation/shared.ts`: a real `YYYY-MM-DD` day, becomes UTC midnight; `""` clears), not `z.coerce.date()`, which turns `null` into 1970-01-01 and "2027-02-30" into March 2.
- A PWD or Solo Parent validity date is refused without its ID number (`updateEmployeeProfileSchema` `superRefine`, same check in `edit-employee-dialog.tsx`), so a cleared number can't leave a date whose chip and dashboard alert point at nothing. Person indexes `{ organizationId, pwdIdValidUntil }` and `{ organizationId, soloParentIdValidUntil }` serve `IdExpiryService`.
- The employee RDO and ZIP are gone (owner decision 2026-11-16). Do not add them back to `Person`: the BIR 2316 export no longer has the employee RDO and ZIP columns (items 5 and 6A), while the employer's RDO and ZIP (`Organization.tax`) stay.
- Government ID and PRC license records: exactly one of `typeCode` / `otherTypeName` on an ID; the catalog code is checked on create and, on update, only when it changes (a retired type or profession stays on entries that use it); the same type or profession may appear twice (a renewal); a validity date is optional and clears with `null`; every query filters by `organizationId` and `personId`; every write is audited (`government-id-record.*`, `professional-license-record.*`); removal is a plain delete. The alert window is `RISK_WINDOW_DAYS` (30) for the chips and the dashboard alike.
- `Person` has no `hiddenFromOthers` field or plugin. Hiding an employee hides the Employee record only (see `visibility.md`).

**Known gaps / mismatches:**
- `PersonService.update` writes `before` and `after` to the audit log, and both contain the statutory IDs and birth date in plain text (`person-service.ts` lines 74-88, 108-116). Anyone with `audit-logs.read` (`scripts/seed.ts`) can read them. Check this against ENGINEERING.md § 35 and any data-minimisation policy.
- The PWD and Solo Parent numbers, and the numbers on government ID and PRC license records, are audited in plain text like the statutory IDs (the person snapshots, and `government-id-record.*` / `professional-license-record.*` entries). Same exposure as the first bullet.
- `PersonService.create` records only names in its audit `after` (`person-service.ts` line 59). The create and update audit payloads are inconsistent.
- The `PATCH /api/employees/[id]` route runs the Person and Employee updates as two writes with no transaction (`src/app/api/employees/[id]/route.ts`). A failure between them leaves a partial edit. Low severity; no ADR covers it.
- `EmployeeRecords.payslips` and `offboarding` run unbounded `find`s with no limit. Acceptable at current scale; not covered by a test.
